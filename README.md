# http-loadgen

[![CI](https://github.com/HollowKaeden/http-loadgen/actions/workflows/ci.yml/badge.svg)](https://github.com/HollowKaeden/http-loadgen/actions/workflows/ci.yml)

Консольный генератор HTTP-нагрузки на Go. Шлёт много параллельных запросов на нужный URL
и считает метрики: латентность (p50/p95/p99/min/max), RPS, сколько было ошибок и каких.
Ядро написано на одной стандартной библиотеке, без внешних зависимостей.

## Зачем это

Это пет-проект для портфолио. Он показывает, что я умею работать с конкурентностью на Go:
пул горутин, каналы, `context`, аккуратная остановка, гонок нет по замыслу. Генератор сделан
максимально общим: бьёт по любому URL и методу.

## Стек

- Go 1.25, модуль через `go.mod`.
- В ядре только стандартная библиотека: `net/http`, `context`, `sync`, `sort`, `time`,
  `flag`, `text/tabwriter`, `encoding/json`. Внешняя зависимость ровно одна,
  `golang.org/x/time/rate`, и она нужна только для необязательного режима `-rps`.
- Тесты: `testing` и `net/http/httptest`.
- CI: GitHub Actions (`vet`, `test -race`, `build`).

## Сборка и запуск

```sh
go build -o loadgen ./cmd/loadgen

# сделать N запросов и выйти
./loadgen -url http://localhost:8000/api/books -c 50 -n 5000

# лить нагрузку заданное время
./loadgen -url http://localhost:8000/api/books -c 100 -d 30s

# отчёт в JSON
./loadgen -url http://localhost:8000/api/books -n 1000 -json

# держать ровно 500 запросов в секунду в течение 30 секунд
./loadgen -url http://localhost:8000/api/books -rps 500 -d 30s

# POST с телом из файла и своим заголовком
./loadgen -url http://localhost:8000/api/books -method POST \
  -H "Content-Type: application/json" -body @payload.json -n 1000
```

`Ctrl+C` в любом режиме останавливает прогон мягко: летящие запросы обрываются через
`context`, метрики считаются по тому, что успели сделать, паники нет.

## Флаги

| Флаг       | Что делает                                              | По умолчанию |
|------------|--------------------------------------------------------|--------------|
| `-url`     | цель, обязательный                                     | нет          |
| `-c`       | сколько воркеров шлют запросы одновременно             | `50`         |
| `-n`       | всего запросов (нельзя вместе с `-d`)                  | нет          |
| `-d`       | как долго лить нагрузку, например `30s` (нельзя вместе с `-n`) | нет  |
| `-timeout` | таймаут одного запроса                                 | `10s`        |
| `-method`  | HTTP-метод                                             | `GET`        |
| `-body`    | тело запроса; `@file` читает тело из файла             | пусто        |
| `-H`       | заголовок `Key: Value`, можно повторять                | нет          |
| `-json`    | вывести отчёт в JSON                                    | `false`      |
| `-rps`     | целевая скорость запросов в секунду (`0` выключает)    | `0`          |

Нужно указать ровно один из `-n` или `-d`. Если флаги заданы неправильно, программа
понятно объяснит ошибку и вернёт ненулевой код выхода.

По умолчанию генератор работает в режиме closed-loop: есть `-c` воркеров, каждый шлёт
запросы один за другим, и темп задаёт сам сервер, насколько быстро он успевает отвечать.
Флаг `-rps` включает open-loop: тогда скорость держится на заданном уровне независимо от
сервера, а `-c` ограничивает, сколько запросов может лететь одновременно. Так удобно
подать ровно N запросов в секунду и смотреть, как при этом растёт латентность.

## Пример вывода

Прогон против тестового сервера, который отвечает со случайной задержкой от 0 до 20 мс,
поэтому p50 получается около 10 мс:

```
$ ./loadgen -url http://127.0.0.1:8099/ -c 50 -n 5000
requests     5000 total, 5000 ok, 0 failed
duration     1.006s
throughput   4971.1 req/s

latency min  0s
latency p50  10.103ms
latency p95  19.022ms
latency p99  19.492ms
latency max  26.114ms

status 200   5000
```

Тот же прогон с `-json`. Формат стабильный, времена отдаются числом в миллисекундах,
чтобы их было легко сравнивать:

```json
{
  "total": 5000,
  "ok": 5000,
  "failed": 0,
  "elapsed_ms": 1005.12,
  "rps": 4974.54,
  "latency_ms": {
    "min": 0,
    "p50": 10.05,
    "p95": 19.03,
    "p99": 19.53,
    "max": 24.4
  },
  "by_status": {
    "200": 5000
  },
  "by_error": {}
}
```

## Как устроено

Три слоя, развязанных друг от друга. Данные текут в одну сторону через каналы. Общего
изменяемого состояния нет: счётчики трогает только агрегатор (share memory by communicating).

```
cmd/loadgen/main.go   флаги в Config, перехват SIGINT, запуск, печать отчёта
internal/config       разбор и проверка флагов
internal/runner       пул воркеров, раздача заданий, отмена по context
internal/stats        агрегатор исходов и перцентили
internal/report       таблица для человека и стабильный JSON
```

Поток простой. `main` разбирает флаги и ловит `Ctrl+C`, `runner` поднимает `-c` воркеров
и раздаёт им задания через канал. Воркеры делят один `*http.Client` (keep-alive соединения
переиспользуются), на каждое задание шлют запрос, замеряют время и кидают исход в другой
канал. Отмена `context` при этом реально прерывает запросы на лету. Исходы читает одна
горутина-агрегатор и копит статистику, поэтому мьютексы не нужны. Когда запросы кончились,
`report` печатает таблицу или JSON.

## Веб-форма: loadgen-web

`cmd/loadgen-web` это HTTP-сервис поверх того же ядра. На сайте-портфолио через него
посетитель может нагрузить сам сайт и смотреть график вживую. Ядро для этого научилось
отдавать метрики по секундам (`stats.CollectLive`, `runner.RunLive`), CLI при этом не менялся.

Чтобы форма не стала способом положить сайт или атаковать кого-то ещё:

- цели только из файла `targets.json`; клиент передаёт `target_id`, долю и длительность,
  а любое другое поле, например `url`, отклоняется целиком (защита от SSRF);
- нагрузка только open-loop и не больше 50% от `max_rps` цели, прогон до 15 с;
- один прогон за раз на всех, пауза 3 минуты после любого прогона, не больше 2 прогонов
  с одного IP за 15 минут (IP из `X-Forwarded-For` только от доверенного прокси);
- аварийный тормоз: больше 5% ошибок или p95 выше 1 с за последние 3 секунды останавливают
  прогон; прогон без зрителей отменяется.

API: `GET /status`, `GET /targets`, `POST /run`, `GET /run/{id}/events` (SSE: окно раз в
секунду, в конце тот же JSON-отчёт, что у CLI с `-json`).

`max_rps` меряет калибровка: ступенчатый рост `-rps`, пока p99 не выше 500 мс, ошибок меньше
1% и генератор держит темп. Запускается вручную на том же сервере, что и цели:

```sh
loadgen-web calibrate -targets targets.json -domain example.ru   # пишет max_rps в файл
loadgen-web serve -targets targets.json -domain example.ru        # API на :8080
```
